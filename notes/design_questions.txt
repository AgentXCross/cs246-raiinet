RAIINet
1. In this project, we ask you to implement a single display that maintains the same point of view as turns switch between player 1 and player 2. How would you change your code to instead have two displays, one of which is from player 1’s point of view, and the other of which is player 2’s point of view?



2. How can you design a general framework that makes adding abilities easy? To demonstrate your thought process for this question, you are required to add in three new abilities to your final game. One of these may be similar to one of the already-present abilities, and the other two should introduce some novel, challenging mechanic. You are required to actually implement these.


3. One could conceivably extend the game of RAIInet to be a four-player game by making the board a “plus” (+) shape (formed by the union of two 10x8 rectangles) and allowing links to escape off the edge belonging to the opponent directly adjacent to them. Upon being eliminated by downloading four viruses, all links and firewall controlled by that player would be removed, and their server ports would become normal squares. What changes could you make in your code to handle this change to the game? Would it be possible to have this mode in addition to the two-player mode with minimal additional work?

Board shape: The plus is the union of a 10x8 and an 8x10 rectangle, so I would use a 10x10 grid with its four corner cells marked invalid. Board (src/core/board.cc and board-impl.cc) would receive the layout instead of relying on hard-coded 8x8 dimensions. A single is_valid_position function would use the layout to validate positions, and moves, firewall placement, port checks, and display queries would all call it rather than duplicating the shape rules. Position would not need to enforce board bounds. Ports and firewalls would be stored by owner, for example in maps from PlayerID to positions.

Players and ownership: I would add P3 and P4 to PlayerID and have Game (src/core/game.cc and game-impl.cc) store players in a vector instead of separate player_1 and player_2 fields. Rather than extending the letter-range checks in src/types.cc, each Link would store its owner, and display labels would be assigned separately (there are 32 links in total). Since a four-player game has no single opponent_of, opponent checks would compare a link's owner with the current player. Abilities such as Download, Scan, and Firewall could then apply to any link not owned by the acting player.

Escaping: Board::move_link currently hard-codes that P1 exits at the bottom and P2 at the top. The layout would instead record the owner of each board edge and which edges each player may exit through. When a move goes off the board, Board would look up the owner of the edge being crossed, allow the download only if it belongs to an adjacent opponent, and otherwise reject the move.

Elimination and turns: When a player reaches four downloaded viruses, Game would eliminate them by removing their links and firewalls from Board and clearing their server ports. next_turn would advance through the player vector, skipping eliminated players. is_game_over would return true when a player has downloaded four data or only one active player remains. In two-player mode, elimination leaves one active player, so the existing rule is a special case.

Displays: Subject would expose the board dimensions, is_valid_position, the player list, and whether a position is a server port. TextDisplay and GraphicsDisplay would use these to draw the configured shape, skip invalid cells, and show each player's information. Once an eliminated player's port is no longer reported as a server port, it displays as an ordinary square.

Supporting both modes: We would define a GameConfig containing the player count, layout, ports, edge owners, and permitted exits. main would select the two-player config by default, or the four-player config with -players 4, and read -ability3, -ability4, -link3, and -link4 for the extra players. Game, Board, and the displays would use the selected config rather than contain mode-specific rules. This requires a one-time refactor away from the current hard-coded 8x8 and two-player assumptions, but afterwards adding a mode means adding a configuration.
